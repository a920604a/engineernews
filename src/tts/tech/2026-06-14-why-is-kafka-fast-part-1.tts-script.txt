Kafka 寫磁碟，卻是業界最快的訊息佇列之一。第一次聽到這件事的人通常會愣一下——磁碟不是比記憶體慢好幾個數量級嗎？

這個直覺沒有錯，但它漏掉了一個關鍵變數：**存取模式**。

---

先說磁碟。傳統 HDD 慢的地方不是傳輸速度，而是「尋道」——讀寫頭要移動到正確的磁軌，這個動作要花 5 到 10 毫秒。聽起來不多，但在這段時間裡，現代 CPU 可以跑幾千萬個指令。

但如果你的讀寫是**循序的**——每次都接著上一次的位置繼續——尋道時間幾乎歸零，磁碟吞吐量可以飆到 500 MB/s 以上，SSD 更高。而且循序存取還有個額外紅利：OS 的預讀機制會提前把你下一步要用的資料載進記憶體，整個感知上就像在讀 RAM。

Kafka 的設計從根本上就是為了循序存取。每個 topic partition 是一個只能 append 的 log 檔案，Producer 永遠往尾巴寫，Consumer 從某個 offset 開始往後讀。讀寫頭只需要往一個方向走，尋道問題直接消失。

---

第二塊拼圖是 **Page Cache**。Linux 核心在磁碟和應用程式之間有一層記憶體快取——你讀過的磁碟資料會留在記憶體裡，下次再讀直接命中快取，不碰磁碟。

很多系統選擇自己在應用層維護 in-memory buffer，Kafka 反其道而行，直接把這件事交給 OS。這帶來幾個好處：

第一，Kafka broker 的 JVM heap 可以維持很小，GC 壓力低。第二，就算 Kafka process 重啟，OS 的 Page Cache 還在，Consumer 重連之後繼續命中快取，不需要重新「熱身」磁碟。第三，當 Consumer 跟得上 Producer 的速度時，Producer 剛寫進去的訊息幾乎立刻就在 Cache 裡，Consumer 讀到的根本不是磁碟 I/O，完全免費。

這也是為什麼 Kafka 的建議配置是把大部分記憶體留給 OS，而不是塞進 JVM heap。

---

第三塊：**Zero-Copy**。這是最有趣的部分。

傳統做法，如果你要把磁碟上的資料送出網路，資料會被搬四次：從磁碟讀進 kernel 的 Page Cache，再複製到 user space，再複製到 socket buffer，最後送到網卡。這中間還要切換四次 kernel 和 user space 的執行環境。

Kafka 改用一個叫 `sendfile` 的 syscall——在 Java 裡對應 NIO 的 `transferTo`。這個系統呼叫讓資料直接從 Page Cache 傳到網卡，完全不需要經過 user space。資料只搬兩次，context switch 只有兩次，而且 CPU 根本不需要親自搬運資料，這件事交給 DMA 控制器，CPU 只需要發出指令就好。

在高吞吐量場景下，比如每秒幾 GB 的資料，省掉的那兩次記憶體複製，直接轉化成更高的吞吐量和更低的延遲。

---

最後，**批次處理**是這一切的乘數。

Producer 把多筆訊息打包成一個 batch 再送，一次 syscall 傳多筆。Consumer 一次拉取一整批，減少網路來回。壓縮也在 batch 層面做，因為多筆格式相似的訊息放在一起壓，壓縮率遠比一筆一筆壓高得多。Kafka 支援 gzip、snappy、lz4、zstd，在網路頻寬是瓶頸的情境下，壓縮直接決定你能不能達到目標吞吐量。

順帶一提，這也是 Kafka 跟 RabbitMQ 這類傳統訊息佇列在設計上的根本差異。RabbitMQ 假設訊息消費完就刪除，需要為每個 Consumer 維護複雜的狀態和 index，讀寫模式更接近隨機存取。Kafka 用「log 加 offset」的模型，訊息保留一段時間，Consumer 自己記 offset，broker 不需要追蹤每筆訊息有沒有被讀過。設計更簡單，循序存取的假設才能成立。代價是訊息不能被個別刪除，但對大多數場景來說，這不是問題。

---

總結三個核心：

一，**循序 I/O**——append-only 的 log 設計讓 Kafka 把磁碟當成高吞吐的順序儲存，完全避開尋道。

二，**Page Cache 加 Zero-Copy**——OS 自動處理記憶體快取，`sendfile` 消除不必要的資料搬運，CPU 省下來的力氣全用在真正有價值的事。

三，**批次是乘數**——所有優化在批次下效益疊加，這才是 Kafka 能撐住超高吞吐的根本原因。

Kafka 快，不是因為用了更貴的硬體，而是因為它在設計上把普通硬體的每一分效能都榨乾了。
