AI Agent 的開發，跟你平常呼叫 LLM API 是兩件完全不同的事。

普通的 API 呼叫是無狀態的——你丟一個 prompt 進去，拿一個答案出來，結束。但 Agent 不一樣。它需要記住自己走到哪一步、根據上一步的結果決定下一步要幹什麼，中途還可能出錯需要重試。這個複雜度，如果你自己手刻，很快就會變成一坨很難維護的 if-else 地獄。

LangGraph 解決的就是這個問題。它讓你用有向圖的方式來描述 Agent 的工作流程——節點是任務，邊是狀態的流向，條件邊則是讓 Agent 根據結果做出不同決策的地方。

這節課我們要建的是一個影片製作 AI Agent。你丟一個主題進去，它自動幫你做研究、寫大綱、展開腳本、生成分鏡描述，最後輸出一整包製作素材。

---

在開始之前，先把一個常見的誤解說清楚：**影片製作 Agent 的核心不是 OpenCV 或 TensorFlow**。那些是電腦視覺和機器學習的工具，跟這裡要做的事情完全是不同層次的抽象。我們要做的是 LLM 推理加工具呼叫，不是訓練模型。這個區分很重要，因為搞錯方向會讓你走很多冤枉路。

---

整個工作流程的邏輯是這樣的：

先從用戶的主題出發，進入研究節點。研究完之後，系統會檢查研究結果夠不夠充分——如果太短或太淺，就重試，最多重試兩次；確認夠用了，才進入下一步寫大綱。大綱寫完，展開各段腳本，再生成分鏡描述，最後打包輸出。這就是整個流程的骨架。

---

現在來看實作。

LangGraph 的核心概念是 **State**——一個貫穿整個工作流程的資料結構。你可以把它想成一個共享的便條紙，每個節點都可以讀它、在上面寫東西，然後傳給下一個節點。

在我們的影片製作 Agent 裡，這個 State 包含：主題、研究筆記、大綱、各段腳本、分鏡描述、錯誤訊息，還有重試次數。這個結構設計好之後，整個 Agent 的狀態流向就完全可以追蹤，debug 也容易很多。

接下來是節點函數。每個節點就是一個函數，接收 State，做一件事，然後回傳更新後的 State。比如研究節點，它拿到主題，呼叫 LLM 要求提供五個關鍵論點和相關事實，拿到回應之後，把研究筆記寫回 State，把重試次數歸零，然後回傳。大綱節點同理，拿研究筆記進去，讓 LLM 規劃五分鐘影片的大綱，解析結果，寫回 State。

這種「每個節點只負責一件事」的設計，讓整個 Agent 的邏輯非常清晰，也容易獨立測試每個環節。

條件邊是讓 Agent 有判斷力的關鍵。以研究這步為例：執行完之後，系統會判斷研究筆記是不是太短——如果字數不夠、而且重試次數還沒超過上限，就讓它回頭重試；夠用了才放行到下一步。這個邏輯用 LangGraph 的 `add_conditional_edges` 寫起來非常直白，可讀性很高。

最後組裝好 graph、傳入初始 State、執行，就可以拿到完整的輸出結果。

---

來回答幾個實務上常碰到的問題。

**為什麼不直接用 LangChain 的 AgentExecutor？**

AgentExecutor 是設計給 ReAct 模式的——就是讓 Agent 自己決定要呼叫哪些工具、呼叫幾次。但我們這個影片製作流程的步驟順序是固定的，LangGraph 在這種情境下可見性更好，你能清楚知道 Agent 走到哪一步、每步的輸入輸出是什麼。

**LLM 呼叫失敗怎麼辦？**

在每個節點函數裡面包 try/except，失敗的時候把錯誤訊息寫進 State 的 error 欄位，然後用條件邊決定是要重試還是終止流程。這個模式讓錯誤處理和業務邏輯分離得很乾淨。

**要讓 Agent 用外部工具怎麼做？**

LangChain 有 tool decorator 可以定義工具，你可以在節點裡直接呼叫，或者用 ToolNode 把工具包裝成 graph 的一個節點——後者讓工具呼叫也變成流程圖的一部分，更容易監控。

---

好，收一下今天的核心重點。

第一，Agent 開發的本質是狀態管理——設計好 State 結構，是整個 Agent 穩不穩的基礎。第二，LangGraph 的節點加條件邊組合，讓你用聲明式的方式處理重試、分支、錯誤這些複雜邏輯，比手刻 if-else 乾淨太多。第三，選對抽象很重要——影片製作 Agent 是 LLM 推理的問題，不是機器學習訓練的問題，方向錯了工具再好也沒用。
