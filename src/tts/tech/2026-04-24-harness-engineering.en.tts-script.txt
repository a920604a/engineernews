Google just dropped the fourth generation of their open-source Gemma models, and buried in that release is something delightfully tiny: Gemma 4 2B. That "2B" means two billion parameters — absolutely minuscule by today's standards, small enough that you can run it on the edge, on your own machine, right at home. Which raises a fun question: can a model that small actually drive an AI agent? I ran a little experiment to find out, and the answer tells a much bigger story than you'd expect. Because the real lesson here is this — sometimes a language model isn't dumb. It just lacks human guidance.

Here's the setup. There's a folder with a file called parser.py. Inside is a function whose job is to pull email addresses out of a chunk of text — except it was written with a bug, so it doesn't catch all the emails. The task: fix parser.py so that a second file, verify.py, passes all its tests. Both files are sitting right there in the same folder as the model.

Now, a language model doesn't magically become an agent on its own. You have to hand it tools. So I set up a dead-simple convention: if the model outputs a little marker, then the word "bash," then a command, the environment runs that command for it. Same idea for Python — output the marker, the word "python," a block of code, and the environment saves it as a file and runs it. So now our tiny model has three powers: it can issue bash commands, it can write Python, and it can run Python.

And here's what happened on the first attempt. Gemma reads the instructions, and its very first reaction is: "There's no parser.py here." Wait — but the file is literally sitting in the same folder. Why does it think that?

Because to the model, its whole world is the text you fed it. Its context contains the *string* "the file parser.py" — but not the file's actual contents. Even though the file physically exists right there, the model has no automatic awareness of it. It can only see the text in front of it. So it improvises. Based on the function name mentioned in the prompt, it hallucinates what parser.py probably looks like, writes out a block of code it imagined, then hallucinates that it verified everything, and proudly declares the task done.

Not what we wanted, obviously. But — and this is the crucial part — this is not a dumb model. It knew exactly what should be in parser.py. It was perfectly capable of writing a correct email parser. It just never realized the actual file was sitting right at its feet. A model's intuition is different from ours. Your human gut says "of course the code comes attached to the problem." The model didn't assume that at all.

So on the second attempt, I added just a few extra lines — fewer than eighty words. And here's the key: these weren't hints about this specific bug. They were general working principles. Basically four things. One: you're in a Linux environment — a nudge to make it comfortable running bash. Two: before you do anything, look around the folder you're in and list the relevant files. Three: before you modify a file, don't just edit blindly — open it and read it first. And four: define what "done" actually means — you have to meet the real criteria before you can call it finished.

Same model. Same task. Completely different behavior. This time it runs "ls" to list the directory and discovers both parser.py and verify.py. Then it runs "cat" on parser.py to print the real contents into its context. Now that it's actually seen the file, it rewrites it properly. Then it runs verify.py to check its own work, sees the tests pass, and finishes. That's exactly what a human wants. Same model — a handful of extra lines of instruction — and the capability gap is enormous.

Which brings us to the big idea. When your AI agent underperforms, where do you actually go to fix it? To answer that, you need to understand what an AI agent is made of. And it turns out there are two parts.

The first part is the large language model itself — that's your Claude, your Gemini, your GPT, whether it's in the cloud or running locally. The second part is all the program scaffolding around it: the code that calls the model, feeds it context, hands it tools, and observes the results. For a long time, that "everything else" had no good name. Now it does. We call it the Harness. A lot of people translate that as "to steer" or "to rein in," and the work of building one is called Harness Engineering. The mental image is perfect: the AI is a powerful horse, and to actually ride it, you need a saddle and reins. That tack — that's the harness.

So there are really two ways to make an agent stronger. Path one: change the model — train a better one, or fine-tune an existing one. Path two: change the harness — build better tack. And path two is the hot topic right now. Anthropic wrote about keeping agents running over long horizons last November, OpenAI published a piece literally called "Harness Engineering" in February, and Anthropic followed with "Harness Design" in March.

And this term shows up in surprisingly practical places. Here's a great example. Claude's subscription users got a notice a while back saying subscription accounts would no longer support third-party harnesses — things like OpenClaw. Why? It comes down to how you pay. There are two models. One is pay-as-you-go: you call the API directly and get billed per token. The other is the subscription all-you-can-eat plan: pay a monthly fee, and in theory call it as much as you want. Providers used to figure the buffet was fine — you're a human, how many instructions can you possibly type in a month? But then along came tools with a heartbeat mechanism, like OpenClaw, that can automatically fire off an instruction every few minutes, around the clock. Suddenly the buffet is bankrupting them. So Claude said: harnesses like OpenClaw can't connect to our models anymore. Which, notice, tells you exactly how the industry now thinks of OpenClaw — it's a harness.

Now, let's zoom out on the terminology, because there's a nice evolution here. Whenever people decide to take a topic seriously, they slap "engineering" on the end. First we got Prompt Engineering, then Context Engineering, and now Harness Engineering. They overlap a lot, but each one emphasizes something different.

Prompt Engineering came first. A language model is basically doing fancy autocomplete — different inputs give you different completions. Back when models were weaker, phrasing the same question two different ways could give you wildly different answers. So people studied how to write prompts, and the most famous magic spell was "think step by step." But those incantations keep losing their power. I mean — why would a model only bother thinking when you *tell* it to? Modern models reason carefully whether or not you chant the magic words. The gap between using the spell and not using it keeps shrinking.

So once the spells faded, people realized something. When a model gets an answer wrong, it's usually not a lack of ability — it's a lack of the right information during that autocomplete. That's Context Engineering: build a system that finds the right context, assembles it into the prompt, and feeds it in. Think of it as a more systematic, automated version of prompt writing.

And then Harness Engineering. What this one emphasizes is getting the task *done*. Because these days, solving a task isn't one question and one answer. It's a multi-turn loop: the human gives a task, the model produces output, the output drives tools, the model observes the tool results, and around and around it goes until an answer emerges. Steering that whole multi-turn dance — that's Harness Engineering. The boundary between context and harness is admittedly a little blurry, since good context is a prerequisite for finishing anything. But the value harness engineering is really trying to capture is: getting the model to do the job well across many turns of interaction.

So how do humans actually steer a model? Let me give you three concrete levers. And this isn't the whole of harness engineering — it's a young, evolving field with lots of competing definitions — but these three are a great start.

Lever one: control the model's cognitive framing using rules written in plain human language. These rules are like the laws of a society. The trick is that before the model does anything, you force these rules into its prompt — and because they're always there, its behavior becomes more predictable. These rules usually live in a file with a fixed name, often agents.md. Think of it as a README written for the language model. How does the model know to read it first? That's hard-coded into the harness. On startup, the harness forces the model to read certain files before it's allowed to do anything else, guaranteeing they land in the prompt.

Now, natural-language rules can't control behavior a hundred percent. Whether the model actually obeys is ultimately up to the model — just like laws are on the books but not everyone follows them perfectly. Some people argue that without hard enforcement it doesn't really count as a harness. But others have given this approach a name: the Natural Language Harness. It's still a harness — the reins just happen to be made of words. Take OpenClaw again: before every conversation, it opens the agents.md in your workspace and makes sure those contents hit the prompt first. That's how the model learns things like — this file is my soul, my memory lives over here, and to dig up older memories I should go search the memory folder with a tool. All of that behavior flows out of agents.md.

And here's a beautiful consequence. Remember how Claude cut off OpenClaw? What do you do? It's almost trivially easy. Anthropic has its own official harnesses — Cowork, and also Claude Code. And by default, on startup, those read a file called CLAUDE.md from your workspace and load it into the prompt. So Cowork's CLAUDE.md is basically OpenClaw's agents.md. To migrate an agent from OpenClaw over to Cowork, all you really do is hand Cowork the same workspace and rename agents.md to CLAUDE.md. And the agent comes back to life, behaving pretty much like before. It might even wake up and go, "Hey, some of this CLAUDE.md looks off — a few of these tools I don't actually have, want me to fix it?" Once you understand how the harnesses work underneath, moving house is nothing.

But does agents.md actually *work*? For a long time everyone just wrote these files by vibes, with zero rigorous research on whether they helped at all. This year, that's finally changing. A paper from January went to GitHub, gathered a big pile of repos containing agents.md, and compared runs with the file versus without it. The result: agents.md tends to make things faster, use fewer tokens, and finish in less time. On average the difference is modest — but for those nasty edge cases that would otherwise drag on forever, it helps a lot more. The catch: this paper only measured *speed*, not *correctness*, because it didn't know what those repos were supposed to do or what the right answers were.

Then a February paper went straight at accuracy. It compared three conditions: no agents.md at all, an agents.md written by the LLM itself, and one written by a human. And the findings are humbling. A human-written agents.md isn't always useful — on some of the stronger models, it seemed to have no effect at all. And the LLM-written version was even worse — usually worse than the human one, and sometimes worse than having no file whatsoever. The takeaway? We humans probably aren't very good at steering these models yet. The agents.md files we write don't reliably help. This is just the beginning — expect much more systematic research, right down to what happens when you add or remove a single sentence.

OpenAI adds a warning here too: agents.md can't be too long. They once tried cramming everything the model should ever know and obey into it — turning it into an encyclopedia, a full legal code. Performance tanked. That giant book ate up most of the model's context, leaving no room to actually work. Their guidance: agents.md should be like a map. It should mostly tell the model *where to go* to find out about something, not stuff all the content inside.

Lever two: control the model's capability boundary by restricting its tools. Even after you rename agents.md to CLAUDE.md, OpenClaw and Cowork still behave quite differently — because their underlying harnesses hand out different tools. OpenClaw runs directly on your computer. It can look at whatever it wants and modify any file on your machine — which is also why it can drive a browser, and could in theory upload videos and become a YouTuber. Cowork, on the other hand, runs in a cloud sandbox — not on your machine at all. For it to see anything of yours, you have to mount a folder, and every single mount requires human consent.

And here's the key detail: that "do you consent to this mount?" dialog is *not* the language model asking. It's a hard-coded line in the underlying harness. Even if you explicitly tell the agent to stop asking for consent, the dialog still pops up — because the model doesn't get a vote. That makes Cowork much safer: everything the model can see is something you personally approved. But safety and convenience are a trade-off. More safety, less convenience. More convenience, less safety. You don't get both.

And lever three: control behavior by defining a workflow and making the model follow it strictly.

So let's come back to where we started. That same tiny Gemma 4 2B — with just a few lines of general working principles added — went from hallucinating a file that was right in front of it to calmly exploring the folder, reading the code, fixing the bug, and verifying its own work. That transformation is the entire point of harness engineering.

So let me leave you with three things to hold onto. First: an AI agent is two parts — the language model, and the harness around it. When it underperforms, the model is only half the picture. Second: you steer a model through three levers — its cognitive framing with natural-language rules, its capability boundary with tool restrictions, and its behavior with defined workflows — and building a better harness is often just as important as swapping in a smarter model. And third, the humbling one: the research is early, and we humans genuinely aren't great at this yet — half the agents.md files we write don't help, and some actively hurt. Keep them short, like a map, not an encyclopedia.

The model isn't dumb. Sometimes it just lacks good human guidance. And figuring out how to give that guidance — that's the whole game right now.
