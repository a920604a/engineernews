你有沒有想過，Claude Code 怎麼能直接幫你查 GitHub PR、跑 SQL 查詢、搜尋 Slack 頻道？這些不是 Claude 本身內建的能力——它是靠一個叫 MCP 的協定外掛進來的。

MCP，Model Context Protocol，是 Anthropic 在 2024 年 11 月發布的開放標準。它要解決的問題其實很具體：AI 代理人要怎麼呼叫外部工具，而且不用為每個工具重新寫一套整合程式碼？

先講 MCP 出現之前的世界。那時候的做法是：你為每個工具定義一個函式，描述它的參數，告訴 AI 它能幹嘛。這方法不是不行，但有個根本問題——耦合。你的 agent 程式碼直接綁死了「我知道有 GitHub、有 Postgres」，工具邏輯跟 agent 邏輯混在一起。每次要加新工具，就得動核心程式碼。

MCP 的解法是把工具定義外部化。工具以獨立的 MCP server 形式存在，有標準化介面。AI agent 啟動時去探索有哪些 server 可用，拿到工具描述，再用標準協定去呼叫。它根本不需要提前知道有什麼工具——符合 MCP 標準，就能即插即用。這個概念很像 USB：你不用管插的是什麼品牌的鍵盤，只要接口對就能用。

架構上，MCP 分三層。最上面是 Host，也就是使用 Claude 的應用程式，像 Claude Code 或 Cursor。中間是 Client，Host 內建的 MCP 協定實作，負責管理跟多個 server 的連線。最底層是 MCP Server，封裝了具體能力的獨立程序——可以跑在本機，也可以是遠端服務。

MCP server 能暴露三種東西：Tools 是 AI 可以主動呼叫的函式，像讀 PR 或執行查詢；Resources 是靜態或動態的資料，像當前開著的檔案或資料庫結構；Prompts 是預設的提示詞模板。傳輸方式上，本機工具通常用 stdio，直接 fork 一個子程序來跑；遠端服務則用 HTTP 或 SSE。

在 Claude Code 裡設定 MCP server 很直接：在設定檔裡宣告 server 名稱、啟動指令、環境變數就好。GitHub、Postgres、Slack 都有現成的官方 server，你直接用 npx 拉下來跑，幾分鐘就接起來了。

這邊有個值得特別提的設計：Tool Search。問題是，每個 MCP server 都帶著自己的工具定義，如果你同時接了十幾個 server，光是這些定義就會把 context window 塞爆。Claude Code 的解法是延遲載入——啟動時只載入工具名稱和 server 描述，詳細 schema 等到真的要用才拉進來。實測下來，context 消耗降低了將近 47%，意思是你可以同時接二十個 server，但 context 用量只比接五個多一點點。

跟其他方案比，MCP 最大的優勢是可重用性。一個 GitHub MCP server，Claude Code 能用、Cursor 能用、Windsurf 也能用。工具作者只需要維護一個實作，不用為每個 AI 平台各自寫一套。這也是為什麼截至 2025 年，已經有 40 多款 AI 編輯器採用了 MCP——業界基本上認可了這個方向。

當然，MCP 不是萬靈丹。如果你只是做一次性的簡單工具整合，直接用 function calling 反而更快。如果你的場景對延遲非常敏感，MCP server 的進程啟動是有初始成本的。這些都是要衡量的。

總結三個核心點：第一，MCP 解決的是工具整合的耦合問題，讓工具可以獨立存在、跨平台重用。第二，Claude Code 的 Tool Search 機制很聰明，大幅降低了多 server 場景下的 context 開銷。第三，對工程師最實際的起點是：先確認你常用的工具有沒有現成的 MCP server，試用幾個感受一下，再決定要不要自己實作。現成的 server 通常已經夠用了。
