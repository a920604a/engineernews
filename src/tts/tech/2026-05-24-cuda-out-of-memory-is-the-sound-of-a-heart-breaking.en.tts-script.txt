If you've trained a deep learning model for more than a week, you've seen it. That brutal red error: RuntimeError, CUDA out of memory. And almost everyone does the same thing next — they throw `torch.cuda.empty_cache()` at it, watch it crash again, and wonder what went wrong.

Here's the thing: `empty_cache()` is one of the most misunderstood functions in PyTorch. What it actually does is return PyTorch's *cached but unused* memory back to the CUDA driver — so other processes can use it. It does absolutely nothing to the memory your tensors are actively holding. If your model is eating 20 gigs and you call `empty_cache()`, you still have a model eating 20 gigs. The crash was never about the cache.

So let's talk about what's actually going on.

PyTorch manages GPU memory in two layers. At the bottom, you have the CUDA driver — the actual physical memory on the card. On top of that, PyTorch runs its own caching allocator. PyTorch grabs large blocks from CUDA upfront and handles sub-allocations internally. This is why when you free a tensor, the memory doesn't immediately show up as free in `nvidia-smi` — it goes back into PyTorch's internal pool first. That speeds up re-allocation, but it also sets up the conditions for a sneaky problem: fragmentation.

Fragmentation is why you get that maddening message — "tried to allocate 512 megabytes, 391 megabytes free, but failed." You have enough *total* free memory, but not enough *contiguous* free memory. It's like trying to park a bus when all the available spots are motorcycle-sized and scattered across a parking lot. The longer a training run goes, the worse this gets.

But fragmentation is usually not your biggest problem. The biggest problems are almost always in your code.

The number one culprit — and the one people miss most often — is running inference without disabling gradients. During inference, you don't need PyTorch to track how every computation flows through the model. But unless you explicitly tell it not to, it does anyway. It stores the entire computation graph in memory, just in case you want to call backward on it. For inference, you never will. Wrapping your inference code in a `torch.no_grad()` context cuts memory usage by 30 to 50 percent, depending on model size. It's free. It costs you nothing. Do it every time.

The second common mistake is accumulating loss values in a loop. Say you're summing up the loss across batches to get an average at the end of an epoch. If you keep adding the raw loss tensor to a running total, you're accidentally keeping the entire computation graph for every single batch alive in memory. None of it gets freed until the loop ends. The fix is simple: call `.item()` on the loss before adding it. That extracts the scalar value and lets the graph get garbage collected immediately.

Third: batch size. This one's obvious, but the fix isn't always "just make it smaller." If you need large effective batches for training stability — which matters more than people realize for things like batch normalization and convergence — use gradient accumulation. Instead of one big batch, you run several small ones, accumulate the gradients, and only update the optimizer every few steps. The model sees the same effective batch size, but your GPU only ever holds a fraction of it at once.

Fourth: mixed precision. By default, PyTorch uses 32-bit floating point — four bytes per value. Switch to 16-bit and you cut memory roughly in half. For the vast majority of models, the accuracy difference is negligible. PyTorch has built-in support for this with `autocast` and `GradScaler`. The scaler handles the numerical stability issues that come with lower precision — it scales the loss before the backward pass and unscales before the optimizer step. It's a near-zero-cost optimization that should probably be your default for any serious training run.

Fifth, and this one's specific to Transformers: gradient checkpointing. Transformer memory scales quadratically with sequence length — twice the sequence, four times the memory. That gets ugly fast. Gradient checkpointing solves this by not storing intermediate activations during the forward pass. Instead, it recomputes them on demand during the backward pass. You trade compute for memory. It typically costs about 30% more training time, but it can bring memory usage down from scaling linearly with model depth to scaling with the square root of it. For long-sequence models, it's often the only option.

So what's the actual diagnosis process when you hit OOM? Read the error message carefully. The ratio between "already allocated" and "reserved" tells you a lot. If allocated is close to total capacity, you have a genuine memory problem — model's just too big. If reserved is much higher than allocated, you're looking at fragmentation. Check your inference paths first — are they all wrapped in `no_grad`? Check your training loops — are you calling `.item()` when you accumulate scalars? Then look at mixed precision, then batch size with gradient accumulation. Gradient checkpointing is your last resort.

And `empty_cache()`? It has its place — clearing memory between unrelated workloads, freeing up space for a separate process. But it is never the fix for a model that's genuinely running out of memory.

Three things to take away from this. One: `empty_cache()` clears the cache, not your tensors — stop reaching for it first. Two: the fastest wins are almost always `torch.no_grad()` on inference paths and mixed precision training — do both before you touch batch size. Three: when you hit fragmentation, the fix isn't a workaround, it's restructuring your memory access patterns so large contiguous blocks are available when you need them. Read the error message, diagnose the cause, then fix the right thing.
