Ring 在 2024 年開放了一個讓開發者很興奮的東西：Appstore API。用白話說，就是你現在可以讓你的 Ring 攝影機「叫你的程式來處理事件」，而不是只能被動地收 App 推播。

有個很具體的場景可以說明這個 API 的威力。假設你住在死巷尾，鄰居的孩子喜歡在你車道上騎腳踏車。你想要的不是「有任何東西移動就通知我」，你想要的是「有陌生車輛進入車道才通知我，而且要能區分自家的車和外來的車」。這就是這個案例要解決的問題，叫做 Driveway Derby。

Ring 官方 App 的通知太廣泛了，路過的行人、風吹樹葉都會觸發，沒辦法設定這種精細條件。但 Ring Appstore API 讓你可以訂閱攝影機的移動偵測事件、拿到觸發事件的影像片段，然後在自己的服務裡做任何後處理。

整個系統的資料流是這樣：Ring 攝影機偵測到移動，事件推給 Ring Appstore API，Ring 呼叫你架的 webhook，你的服務去下載影像，丟給電腦視覺分析，判斷結果決定要不要發通知。這個鏈路端對端大概三到八秒，包含下載和分析的時間。

認證這塊用的是 OAuth2。你要先到 Ring 的開發者程序申請帳號，審核可能要等幾天到幾週，他們要知道你的 App 要做什麼。拿到 client_id 和 client_secret 之後，就走標準的 OAuth2 授權碼流程——引導使用者去 Ring 的授權頁面，使用者同意之後，Ring 把授權碼傳回你的 callback 端點，你再拿這個碼去換 access token 和 refresh token。

有幾個眉角要注意。第一，整個授權流程需要你有公開的 HTTPS 端點，本機開發的時候要用 ngrok 之類的工具打洞，但生產環境記得換成真正的服務，ngrok 免費版有請求限制而且重啟 URL 會變。

Webhook 這端，Ring 會在每次事件觸發時打過來，你要驗簽名確保請求是真的來自 Ring，然後把影像分析的工作丟到非同步佇列處理。不要在 webhook handler 裡做慢操作，不然 Ring 會以為你掛了。

電腦視覺的部分這個案例用 OpenCV 的背景減除法。概念上就是把影片每一幀和背景比較，找出移動的物體，再根據物體的大小來判斷是不是車輛。面積很小的移動——樹葉、貓、小蟲——直接過濾掉，只有夠大的移動才進入後續判斷。對一般大小的車輛，白天準確率可以到九成以上，但夜間或強逆光會掉到七成，因為 Ring 夜視模式輸出的是灰階影像，分析邏輯要另外調整。

踩坑的地方主要是兩個。一是 Ring 影像下載的速率限制，短時間大量請求會被限速，設計架構時要把佇列和重試機制算進去。二是 OAuth2 的 refresh token 管理，access token 有效期限到了要自動用 refresh token 換新的，沒處理好的話系統會靜默失效，你完全不知道它已經停止運作了。

整理一下這個案例最核心的三件事。第一，Ring Appstore API 真的把 Ring 從封閉設備變成一個可程式化的平台，適合有精細條件控制需求的場景。第二，這套架構的關鍵是 webhook 加上非同步處理，速率限制和重試是架構設計要先想好的，不是事後補的。第三，電腦視覺在這類場景下很實用，但光線條件對準確率影響很大，部署前要在實際環境充分測試。
