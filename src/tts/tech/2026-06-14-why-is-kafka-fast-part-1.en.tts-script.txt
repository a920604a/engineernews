Kafka writes everything to disk, and somehow it's one of the fastest message queues in production. That sounds like a contradiction. Disk is slow, memory is fast — we all learned that. So what's going on?

The answer is that "disk is slow" is only half the story. *How* you access disk is what actually determines speed.

Let's start with the mechanical reality. A traditional hard drive has a physical arm that has to move to the right position before it can read anything. That movement — called a seek — takes five to ten milliseconds. That might sound tiny, but in that time a modern CPU can execute tens of millions of instructions. Seek time is the killer.

But here's the flip side: if you never seek — if you just keep reading or writing in one continuous direction — seek time basically disappears. Sequential disk throughput can hit five hundred megabytes per second on spinning disk, and way higher on SSD. That's competitive with a lot of in-memory workloads.

Kafka is architected entirely around this insight. Every topic partition is an append-only log. Producers always write to the end. Consumers always read forward from a saved position called an offset. The read head moves in one direction. Sequential access, by design.

And because access is sequential, the Linux kernel can kick in with something called read-ahead. It predicts what you'll need next and pre-loads it into memory before you even ask. That pre-loaded memory is called the Page Cache, and it's the second big piece of the puzzle.

When you read data from disk on Linux, the kernel stores a copy in the Page Cache. The next time anyone asks for that same data, it comes from memory — not disk. Kafka leans into this aggressively instead of managing its own in-memory buffer like a lot of systems do.

This has a few really nice properties. First, the Kafka broker process itself stays small. It doesn't need a huge heap, which means less garbage collection pressure on the JVM. Second — and this is the clever bit — the Page Cache is managed by the OS, not by the Kafka process. So if Kafka crashes and restarts, the cache is still there. A JVM heap gets wiped on restart; OS page cache survives. Consumers keep reading from memory like nothing happened.

Third, when consumers are keeping up with producers — which is the normal case — a message that was just written is already sitting in Page Cache. The consumer reads it directly from memory. Physical disk doesn't get touched at all.

This is why Kafka's setup guides tell you to give most of your broker's RAM to the OS rather than the JVM heap. You *want* the operating system using that memory for Page Cache.

Now, even if data is already in the Page Cache, you still have to move it from memory to the network card to send it to consumers. In the traditional approach, that journey is surprisingly expensive. Data moves from the kernel's cache into user space, then back into a socket buffer in the kernel, then to the network card. Four copies, four switches between user space and kernel space. The CPU has to orchestrate all of it.

Kafka instead uses a system call called `sendfile`. With `sendfile`, data goes from the kernel's Page Cache directly to the network card buffer — two copies, two context switches — and crucially, the CPU doesn't actually touch the data itself. A hardware controller called the DMA chip handles the transfer. The CPU is freed up entirely.

This is what people mean by Zero-Copy. When you're pushing gigabytes per second, eliminating those extra copies and context switches translates directly into higher throughput and lower latency.

And then there's batching, which multiplies all of this. Producers bundle multiple messages into a single batch before sending. Consumers pull a batch at a time. Fewer syscalls, fewer network round trips. Compression also kicks in here — similar messages bundled together compress far better than individual messages do. When network bandwidth is the bottleneck, that compression can be the thing that gets you across the throughput target.

So to pull it all together: three core takeaways.

First, disk isn't inherently slow — random access is slow. Sequential disk I/O is fast, and Kafka's append-only design ensures every read and write is sequential.

Second, Kafka doesn't fight the OS — it delegates. By relying on Linux's Page Cache instead of its own buffer, Kafka gets memory-speed reads for free, keeps its JVM footprint small, and stays resilient across restarts.

Third, Zero-Copy removes the CPU from the data path. Using `sendfile`, data moves from cache to network card without the CPU touching it, cutting copies and context switches in half at every throughput level.

The elegant part is that all three of these optimizations depend on the same foundational choice: the append-only log with consumer-managed offsets. Because nothing is ever modified or deleted, sequential access is always guaranteed. That simplicity is what makes everything else possible.
