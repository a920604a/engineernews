程式碼難維護，很多時候不是邏輯有多複雜，而是模組之間耦合太緊——改一個地方，就要追著整條鏈跑。今天要聊的依賴注入，就是用來解開這條鏈的。

依賴注入的核心思想只有一句話：不要讓類別自己建立它所需要的東西，而是從外部傳進來。聽起來很簡單，但這個小小的改變，會讓你的程式碼可測試、可替換、可演進。

先從一個有問題的例子開始。假設你有一個 `OrderService`，裡面直接 new 了一個 `ConsoleLogger`。這帶來兩個麻煩：第一，你沒辦法在單元測試裡換掉這個 logger，跑測試時 log 就真的印出來了，甚至寫進真實系統；第二，有一天你想換成雲端的 logger，你就得去改 `OrderService` 的內部，不是加功能，而是去動它的實作細節。

解法分四步。

第一步，定義介面。不要綁定具體實作，而是先說清楚「我需要什麼能力」。比如 Logger 介面只要求有 log 跟 error 兩個方法，只要你實作了這兩個，我就接受。介面是一份合約，不管你底層怎麼做。

第二步，實作介面。正式環境用 `ConsoleLogger`，把訊息印到 console；測試環境用 `SilentLogger`，這個實作什麼都不做，但它完整符合介面。這樣測試時就能消音，完全不影響真實系統。

第三步，透過建構子注入。`OrderService` 的建構子改成接收一個 Logger，而不是自己建立。這樣 `OrderService` 就不再知道 logger 的具體型別，它只知道「我有一個實作 Logger 介面的東西」。正式環境傳 `ConsoleLogger`，測試環境傳 `SilentLogger`，使用者的程式碼完全不需要改。

第四步是進階的，當依賴鏈變長——A 依賴 B、B 依賴 C——手動組裝就開始變繁瑣。這時可以用 DI 容器來管理。容器的概念是：你先把所有依賴都登記進去，要用的時候再跟容器要。生產環境通常會用成熟的框架，TypeScript 生態裡常見的是微軟出品的 tsyringe，輕量好用；或是功能更完整的 InversifyJS，適合大型專案；如果你在用 NestJS，它自己就內建了 DI 容器。但不管用哪個框架，先搞懂手動注入的原理更重要。

幾個常見問題也值得提一下。有人會問：這樣不是要多寫很多介面，很麻煩嗎？答案是，只有在你確定需要替換實作的地方才值得抽介面。如果一個類別只有一個實作，你確定不會換，直接傳類別也沒問題。不要過度設計。

另外，React 的 Context 其實就是一種 DI 機制——讓子元件可以取得從上層注入的依賴，比如登入狀態或主題設定，而不需要一層一層傳 props。概念完全一樣，只是框架不同。

好，收尾來整理三個核心帶走：第一，依賴注入的本質是「從外部傳入，而不是內部建立」，這讓你的模組邊界變清晰。第二，介面是關鍵，有了介面才能在測試和正式環境之間自由替換實作。第三，容器和框架是工具，手動注入的概念才是根本，理解了原理，框架只是省力的手段。
