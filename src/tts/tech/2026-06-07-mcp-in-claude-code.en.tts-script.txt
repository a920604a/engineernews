If you've ever wondered how Claude Code can read a GitHub pull request, query your Postgres database, or search through Slack — that's not something Claude was born knowing how to do. Those capabilities are plugged in through something called MCP, the Model Context Protocol.

Anthropic released MCP as an open protocol in November 2024, and the design goal is actually pretty elegant: let AI agents connect to any external tool without writing custom integration code for each one. Think about what USB did for hardware peripherals — before USB, every device had its own proprietary connector. MCP is trying to do the same thing for AI tools.

Here's the problem it's solving. Before MCP, if you wanted an AI agent to call GitHub or query a database, you'd write a function for each tool, define what parameters it takes, and bake that description into your agent's system prompt. The agent's code directly knows "there's a GitHub tool, there's a Postgres tool." Every time you add something new, you're cracking open the agent's core logic. Your tools and your agent are tangled together.

MCP's approach is to pull the tools outside. Tools live as independent MCP servers with a standardized interface. When the AI agent starts up, it discovers which servers are available, pulls down the tool descriptions, and then calls them using the standard protocol. The agent doesn't need to know about any specific tool in advance — if it speaks MCP, it can plug in.

Architecturally, there are three layers. The Host is the application using Claude — Claude Code, Cursor, whatever. The Client is the MCP protocol implementation baked into that host, managing connections to multiple servers. And the Servers are independent processes that wrap specific capabilities — GitHub, Postgres, Slack, or whatever custom tool you've built.

Those servers can expose three kinds of things: Tools, which are functions the AI can actually call — like "read this PR" or "run this SQL query." Resources, which are data the AI can read — like your currently open files or a database schema. And Prompts, which are preset prompt templates.

For how servers communicate, there are three transport modes. The most common for local tools is standard IO — the host just forks a subprocess and talks to it directly. For remote services, there's Server-Sent Events, which handles one-directional streaming. And in 2025, they added HTTP Streamable for true bidirectional communication with remote servers.

Setting this up in Claude Code is straightforward. In your settings file — either global or per-project — you list your MCP servers by name, tell Claude Code what command to run to start each one, and pass in any environment variables they need, like API tokens. Two lines of config and suddenly Claude Code can talk to GitHub.

Now, one real engineering challenge MCP creates: every server ships with detailed descriptions of all its tools, and if you connect a bunch of servers at once, those descriptions eat up a significant chunk of your context window before you've even started working. Claude Code solved this with something called Tool Search. At session startup, only the tool names and server descriptions load. The full schemas for individual tools are fetched lazily, only when they're actually needed. That one optimization cut context consumption by roughly 47%. In practice, connecting 20 MCP servers costs barely more context than connecting 5.

How does MCP stack up against the alternatives? Direct function calling — where you just define the tools inline — is simpler and has no extra server to run. But your tool definitions are locked into your agent's code and can't be shared. LangChain has a rich Python ecosystem of tools, but you're framework-locked and it doesn't travel cross-language. Raw REST API calls give you maximum flexibility, but then the AI has to understand each API's quirks with no standardization at all.

MCP's real edge is reusability. A GitHub MCP server can be shared by Claude Code, Cursor, Windsurf, and any other MCP-compatible tool. The team that builds the server maintains one implementation, and everyone benefits.

That said, MCP isn't always the right call. If you've got a one-off simple integration, just write a function — it's faster. If the tool doesn't need to be shared across AI applications, the overhead isn't worth it. And if your use case is latency-sensitive, keep in mind there's some startup cost to spinning up MCP server processes.

So here's where I'd leave you with three things.

First: MCP is real infrastructure standardization, not just hype. The fact that Cursor, Windsurf, and 40-plus editors adopted it within a year of launch signals genuine industry alignment.

Second: the decoupling is the point. Separating tool definitions from agent logic is the same bet software engineering has always made on interfaces over implementations — it just scales better.

Third: the practical starting point is dead simple. Before you build anything custom, check whether your tools already have MCP servers — GitHub, Slack, Postgres, most major services do. Try connecting a couple, see how AI integrates into your workflow. Build your own server only once you know what's missing.
