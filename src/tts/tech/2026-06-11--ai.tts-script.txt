大多數人用 AI 的方式，就是打開 ChatGPT 或 Claude，貼一個問題，看看它說什麼。這是「在用 AI」。但「善用 AI」是完全不同的一件事。

善用 AI 的人，更像是在和一個知識淵博但需要明確指引的同事合作。你要負責給方向，你要負責驗證輸出，你要知道什麼任務適合交給它、什麼不適合。今天分享五個讓 AI 真正有用的具體做法。

---

第一點，context 的品質決定回答品質。

AI 本質上是個預測機器，它只能根據你給的東西生成回應。你給得越模糊，它產出的東西就越通用、越沒用。

舉個例子，「幫我寫一個登入功能」——這是壞的 prompt。好的版本會告訴它：你用的是 Next.js 14 加 Supabase、已有的 client 設定在哪個檔案、你需要什麼、不需要什麼。這兩個 prompt 生成的結果，差距可能是「直接能用」和「還要改半小時」的區別。

另一個實用技巧是在 prompt 開頭放角色設定，比如告訴它「你是一個熟悉 Rust 的後端工程師，正在 review 以下程式碼，重點關注 ownership 問題」。這樣它的回答就會聚焦在你真正關心的地方。

---

第二點，多輪對話遠勝於一次搞定。

很多人把 AI 當成「一次輸出一個答案」的工具，試圖用一個超長 prompt 一次解決複雜問題。這個方式通常效果差。

原因很簡單：AI 一次生成大量輸出時容易失焦，而且如果方向一開始就跑偏，你要從頭來。多輪對話讓你每一步都能糾正。

實際操作上，第一輪先讓它告訴你它打算怎麼做，不用寫程式碼；第二輪才讓它執行一個具體步驟；第三輪 review、指出問題、讓它修。把 AI 當成需要 pair programming 的工程師，而不是一個你丟需求進去、等它吐出成品的黑盒子。

---

第三點，知道 AI 什麼時候會說錯。

這是「善用」和「誤用」之間最大的差距。

最危險的情況是 factual recall，也就是問它具體的事實——某個 library 的版本號、某個 API 的確切參數、任何 knowledge cutoff 之後發生的事。AI 會非常自信地說出過期或根本不存在的資訊。數字計算也一樣，它看起來在算數，但實際上它在預測「這個問題的答案通常長這樣」，不是真的在算。

相對可靠的是推理和分析類任務——解釋這段程式碼在做什麼、比較兩種架構的取捨、幫你重構成更清楚的版本。這類任務 AI 表現穩定得多。

原則是：任何 AI 說出的具體事實，包括 URL、版本號、函式名稱、benchmark 數字，都要去一手來源確認。

---

第四點，把 AI 接進工作流程，不是只用聊天介面。

最大的效益不在聊天框，在 pipeline。

工程師可以在 git commit 前自動讓 AI review 這次的 diff，專注找安全問題和明顯 bug；可以把 API 的 route 程式碼餵給它，自動生成 OpenAPI 文件；可以在 cursor 或 claude-code 裡標記一個函式，讓它幫你寫 unit tests，包含 edge cases，人工 review 後加進 test suite。

至於不同工具的取捨：Claude Code 適合複雜多步驟任務、理解大型 codebase，但每次需要給比較多 context；Cursor 適合快速的小修改，複雜任務容易跑偏；GitHub Copilot 的 inline suggestion 和 IDE 整合體驗好，但不適合需要深思的大型重構。選對工具，效益差很多。

---

第五點，只讓 AI 做你有能力驗證的事。

這是最重要、也最容易被忽略的原則。

很多人讓 AI 寫一個自己完全看不懂的模組，然後直接 merge。問題不是 AI 寫的東西一定差，有時候品質真的很好。問題是你沒有能力判斷它是否正確，這讓錯誤進 production 的機率大幅提高。

善用的版本是：AI 幫你寫的程式碼，你能讀懂每一行；AI 幫你分析，但最後的判斷是你的；AI 生成的文字，你有能力驗證事實的部分。

AI 最適合「讓有能力的人做得更快」，而不是「讓沒能力的人繞過能力要求」。這個差別，決定了 AI 在你手上是加速器還是風險源。

---

總結三個核心要點：

第一，context 品質決定輸出品質，給得越具體，AI 越有用。

第二，多輪對話加上接進工作流程，效益遠大於只在聊天框裡問問題。

第三，任何 AI 輸出的具體事實都要驗證，而且只讓它做你有能力驗證的任務。

「善用 AI」不是學更多 prompt trick，是改變你和 AI 協作的心態：你是主導者，AI 是執行者，輸出需要你來把關。現在是練習這件事的最好時機，等 AI 更強再說——這個策略已經落後了。
