書籍電商平台，面試官最愛出的經典題之一。很多人第一反應是「不就是一般電商加個書架嗎」——錯，書籍搜尋的複雜度遠超一般商品，你要同時處理書名、作者、ISBN、類型，甚至有人會說「那本講二戰的書，封面是紅色的」這種模糊描述。加上實體書和電子書的庫存邏輯完全不同，這題其實有很多值得深挖的決策點。

先說設計哲學。面試官不是要你背標準答案，他想看的是你如何思考取捨。所以第一步永遠是需求澄清：規模多大？DAU 是多少？要不要支援第三方賣家入駐？有沒有訂閱方案？

數感很重要。假設一百萬 DAU，每人每天五次搜尋、十次頁面瀏覽、0.1 次下單，換算下來搜尋 QPS 大概五十幾，讀取一百出頭，寫入不到兩。這個規模，老實說一台資料庫加讀寫分離就夠了。你不需要微服務。

---

來看三個核心設計決策。

**第一，搜尋架構。**

資料庫的 LIKE 查詢在這裡完全不夠用，你需要 Elasticsearch。推薦的做法是 PostgreSQL 加 Elasticsearch 雙寫：用戶的搜尋請求打到 Elasticsearch 拿到書籍 ID 列表，再去 PostgreSQL 或 Redis 快取撈完整的書籍資料，最後組合回傳。

這裡有個取捨要說清楚：Elasticsearch 跟主資料庫之間會有短暫的不一致。剛上架的書可能幾秒到幾十秒才會出現在搜尋結果裡。對大多數書籍平台，這是可以接受的最終一致性，但你要主動說出來，不能讓面試官以為你沒想到。

**第二，庫存管理。**

實體書有限庫存，超賣是災難；電子書理論上無限，但可能有同時借閱數量的授權限制，邏輯完全不一樣。

對實體書，最安全的做法是 PostgreSQL 的悲觀鎖。簡單說就是：拿鎖、確認庫存大於零、扣庫存、建訂單、釋放鎖，這個事務是原子的。高並發場景下，你可以在前面加一層 Redis 做庫存預扣，讓大部分「庫存不足」的請求在快取層就擋掉，不用每次都打資料庫。但要注意 Redis 和 DB 之間如果不一致，可能會有短暫超賣的風險——這個取捨要講清楚。

**第三，訂單狀態機。**

訂單的狀態轉換一定要用有限狀態機來設計。流程大概是：建立 → 等待付款 → 已付款 → 處理中 → 已出貨 → 已送達，中間某些節點可以取消。每個狀態轉換要對應一個明確的事件，要記時間戳和原因，而且每個操作必須是冪等的——就是重複觸發同一個事件不會造成重複操作。

另外，退款邏輯不要塞進訂單狀態機裡，獨立出來做另一個狀態機，維護起來清晰很多。

---

說到架構選型，單體 vs 微服務這個問題，很多人會本能地衝向微服務，因為看起來「比較現代」。但真實的反例就是 Amazon，早期也是單體，規模到一定程度才遷移服務化。

白話比較一下：單體開發快、部署簡單、除錯容易，就是難以針對單一模組水平擴展；微服務可以獨立擴展、技術棧靈活，代價是分散式系統的所有複雜度——網路延遲、分散式事務、維運成本。中間有個折衷叫模組化單體，邏輯上隔離但還是跑在同一個進程，適合過渡階段。

**什麼時候才值得上微服務？** 搜尋流量是訂單流量的一百倍以上、不同服務需要不同技術棧、有獨立的團隊負責不同業務領域——這些條件缺一不可。DAU 不到十萬？小團隊？業務模型還在快速變化？請先不要碰微服務。

---

最後整理三個核心要點。

一，面試重點不是你用了幾個技術名詞，而是你能不能清楚說出每個決策背後的取捨。「我選 X 而不是 Y，因為在這個規模下 X 的維護成本更低，Y 帶來的效能提升不值得這個複雜度」——這樣的回答比羅列一堆工具名稱有說服力得多。

二，數感先行。先做容量估算，讓數字告訴你哪裡是真正的瓶頸，再針對瓶頸做設計，而不是每個地方都加快取都用微服務。

三，有限狀態機 + 冪等設計是訂單系統的基礎，不是加分項，是必答項。只要你碰訂單，這個概念就一定要說出來。
