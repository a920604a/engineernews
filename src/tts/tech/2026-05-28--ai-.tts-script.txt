你的 AI agent 上線了，功能超酷，但月底帳單一出來，你就想把它下架。

這是 2025、2026 年 AI 工程師的新現實：LLM API 單價確實降了，但 agent 的 token 用量是以倍數在成長。一個「看起來很簡單」的工作流程代理人，每天可能輕鬆燒掉幾百美元。問題不在你的功能太多，問題在你的架構方式。

費用爆炸通常來自三個地方，我們一個一個拆開來說。

第一個問題，也是最常見的：**你用了比任務需要更強、更貴的模型**。

很多工程師的預設心態是「反正用最強的就對了」，所以不管什麼任務都丟給 Opus 或 GPT-5。但你想想，「從收據裡抓出金額和日期」這種任務，格式固定、邏輯簡單，根本不需要頂級推理能力。同理，「判斷這個 issue 應該分給哪個 team」，需要的是理解語意，不是解數學題。

正確做法是建立一個模型階層：便宜的模型負責分類、提取、路由這類規則性強的任務；中等的模型負責摘要和程式碼生成；最強的模型只保留給真正需要多步規劃、複雜推理的場景。

成本差距有多大？Claude Haiku 和 Claude Opus 之間，同樣的任務，Haiku 可能只花 Opus 費用的百分之零點五。沒有打錯，零點五趴。

第二個問題：**tool call 沒有深度限制**。

agent 在遇到卡關或錯誤的時候，很容易陷入無限迴圈，不斷呼叫工具、不斷嘗試。每多一輪 tool call，就多一次 LLM 呼叫費用，加上整個 context 重新傳一遍的 token 費用。解法很直接：設一個最大迭代次數，比如十次，超過就強制停止、記錄日誌、回傳部分結果。這個上限不只是成本保護，也是讓你的系統更可觀測。

第三個問題：**context window 的浪費**。

每次呼叫 LLM 都把整個對話歷史全部傳進去，是 token 浪費最大的來源之一。兩個策略可以顯著改善：

一是滑動視窗，只保留最近幾輪對話，而不是從頭到尾全部帶著走。

二是壓縮 tool 回傳結果。搜尋工具可能回傳一整篇文章，但 agent 真正需要的只是標題和摘要。把原始結果在傳回給 LLM 之前先過濾一遍，可以把 token 用量砍掉一大截。

另外還有一個常被忽略的優化點：**快取重複呼叫**。如果你的 agent 在不同任務裡一直重複查同一個使用者資料、或者同樣的資源，每次都重新呼叫是純粹的浪費。加個記憶體快取，同樣的資料只查一次。

最後有一個常見的誤解要特別說：降到便宜的模型，會不會讓 agent 變笨、錯更多、反而更貴？答案是：取決於任務類型。結構化提取和分類，Haiku 通常夠用，準確率沒有明顯差異。但如果你強行把需要多步推理的任務降到弱模型，它錯的機率提高，重試次數增加，總費用反而可能更高。所以正確順序是：先測準確率，再做成本決策，不要反過來。

總結三個核心要點：

一，依任務複雜度選模型，不是全部用最強的，成本差距可以是兩個數量級。

二，永遠給 tool call 設最大迭代次數，防止無限迴圈燒錢。

三，精簡 context 傳遞，用滑動視窗加壓縮 tool 結果，這兩個加起來通常能把 token 用量砍掉三到五成。

AI agent 的成本優化，本質上是一個「精準匹配」的問題，不是功能的取捨，而是把對的工具用在對的地方。
