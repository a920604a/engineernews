Picking the wrong hardware for AI workloads isn't just a performance problem — at scale, it's a billing nightmare. CPU, GPU, TPU: three very different bets, and most engineers default to GPU without asking whether that's actually the right call.

Let's break down what each one actually does, where each one fails, and how to make the decision without burning money.

---

Start with the CPU. Modern server chips — your Intel Xeons, your AMD EPYCs — are built around one philosophy: make each core as smart as possible. They predict which branch your if-else logic is going to take before it gets there. They reorder instructions on the fly to keep execution flowing. They maintain this whole hierarchy of caches — L1, L2, L3 — because main memory is roughly a hundred times slower, and they can't afford to wait.

All of that sophistication makes CPUs exceptional at the messy, branchy, unpredictable work of running web servers, database queries, complex business logic. But a modern server CPU might have 8 to 64 cores. That's it. When your task requires doing the same operation millions of times simultaneously, you've hit the ceiling.

For AI specifically, CPUs shine in places people underestimate: real-time inference for small models where you're serving one request at a time, tokenization, data cleaning, pre- and post-processing pipelines. Sometimes CPU inference on a compact transformer model is genuinely competitive with GPU — and a lot cheaper.

---

Now the GPU. The design philosophy is almost the exact opposite. Instead of a handful of brilliant cores, you get thousands of simple ones. An NVIDIA H100 has nearly 17,000 CUDA cores, plus dedicated Tensor Cores on top of that. These cores can't do complex logic well, but they can execute the same mathematical operation across massive datasets simultaneously — and that's precisely what matrix multiplication in a neural network looks like.

Training a deep learning model is essentially enormous batches of matrix math, repeated across billions of parameters. GPUs were built for this, even if that wasn't the original intention.

But here's where a lot of teams get it wrong. GPU isn't universally better. If you're doing real-time inference where one request comes in at a time — batch size of one — you can actually be slower on a GPU than a CPU. The reason is data transfer overhead: moving data between CPU memory and GPU memory takes time, and if your actual compute is small, that overhead dominates. You're paying for a sports car but only driving it across a parking lot.

The same problem hits control-flow-heavy logic. GPUs execute in what's called SIMT mode — Single Instruction, Multiple Threads. When your code hits a branch and different threads need to go different directions, the GPU serializes them. Performance degrades fast.

So think of GPU decision-making as a simple filter. If your work has complex branching logic, CPU first. If you have large batches of uniform computation, GPU. If you have small batches with no large model, CPU might be cheaper and just as fast.

---

Then there's the TPU — Google's custom silicon, purpose-built for neural network training. They've been using these internally since 2016, and they train their largest models, PaLM, Gemini, on TPU Pods.

The key innovation is something called a systolic array. In a traditional GPU, each compute unit reads data from memory, does its calculation, writes back to memory. In a systolic array, data flows through a grid of compute units like a current. Each unit does its multiplication as data passes through, then hands off to the next unit. No repeated memory reads. No repeated writes. This slashes memory bandwidth pressure dramatically — and memory bandwidth is usually the bottleneck in large model training.

The tradeoff is rigidity. TPUs are optimized for dense matrix operations with simple control flow. They don't have native PyTorch support — you're compiling through XLA, Google's intermediate layer. Small batches, irregular models, anything with messy branching — TPUs aren't the right fit. And you can only access them through Google Cloud; there's no buying hardware.

---

Now the part most articles gloss over: cost.

A CPU instance with 8 cores and 32 gigs of RAM runs around 38 cents an hour on Google Cloud. A T4 GPU — an older, mid-range card with 16 gigabytes of VRAM — lands somewhere between 35 and 70 cents depending on configuration. So for small to medium inference workloads, GPU and CPU are actually in the same ballpark.

Step up to an A100 with 40 or 80 gigs of VRAM and you're at roughly 3 to 4 dollars an hour. An H100 — the current top-end for training — runs 6 to 10 dollars an hour. A TPU v4 sits around 3 dollars an hour and is genuinely competitive for JAX and TensorFlow workloads at scale.

The number that matters most isn't the hourly rate — it's utilization. If your GPU is only 30% utilized, you're paying full price for a third of the value. The first metric to pull when auditing a GPU deployment is the `gpu_util` field from the monitoring tools. If that number is low, you're either undersized on batch, or you shouldn't be on GPU at all.

---

So how do you actually decide?

If you're running an online inference service with strict latency requirements and small batch sizes, start with CPU or a T4. Only escalate to A100 or H100 if you've measured that GPU utilization is consistently high. If you're training large models in PyTorch, H100 clusters are the standard. If you're on JAX or TensorFlow and running at serious scale, TPU v4 or v5 on Google Cloud is genuinely the optimal choice — it's what the workload was designed for.

For local development and experimentation, one thing worth knowing: Apple Silicon's unified memory architecture — where CPU and GPU share the same memory pool — gives surprising advantages for medium-sized model inference. And consumer GPUs like the RTX 4090 can match A100 training efficiency for workloads that fit in their VRAM, at a fraction of the cloud rental cost.

---

Three things to take away from this.

First: GPU is not the default answer for AI. It's the answer when you have large batches of uniform matrix math and high utilization. Otherwise, you might be paying a GPU premium for CPU-grade throughput.

Second: TPU is a specialist tool. Exceptional for dense matrix workloads in the JAX and TensorFlow ecosystem, especially at Google Cloud scale. Outside that specific context, the friction of XLA compilation and the lack of PyTorch support usually outweigh the performance gains.

Third: utilization is the real metric. The hardware decision and the architecture decision are linked. Choosing the right chip doesn't matter if your serving infrastructure isn't keeping it fed. Measure first, then decide.

Hardware selection used to be boring. Now it's a genuine engineering decision with real cost consequences. Match your workload's computation pattern to the right architecture — don't just reach for GPU because it sounds like the AI thing to do.
