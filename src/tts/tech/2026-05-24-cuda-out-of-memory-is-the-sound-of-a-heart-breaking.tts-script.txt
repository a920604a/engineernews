CUDA out of memory。這四個字，每個在跑深度學習訓練的人都看過，大概也都心跳漏拍過一次。

然後你做了什麼？加了一行 `torch.cuda.empty_cache()`，然後繼續跑，然後繼續掛。今天我們來聊清楚這件事——為什麼那行沒用，以及你真正應該做什麼。

先把最重要的事說清楚：`empty_cache()` 只是把 PyTorch 快取但暫時閒置的記憶體還給 CUDA driver，讓其他程序能用。你的張量佔著的記憶體？完全動不了。這是最普遍的誤解，幾乎每個人都踩過。

那 OOM 真正的根源是什麼？有五個，我們一個一個說。

第一，也是最容易忽略的：**推論時忘了關梯度**。PyTorch 預設會記住整個計算圖，因為它假設你之後要做 backward。但如果你是在跑推論，根本不需要梯度，這些計算圖全是白白佔空間。解法就是用 `torch.no_grad()` 把推論包起來。這一個動作，視模型大小，可以省下 30 到 50% 的 GPU 記憶體。是的，就這麼多。

第二，**在迴圈裡累積 loss 的方式不對**。很多人會在迴圈外面開一個變數，然後每個 batch 把 loss 加進去做統計。問題是，如果你直接把 PyTorch 的 tensor 加進去，你就在把整個計算圖的參考一路牽著，記憶體根本釋放不掉。正確做法是呼叫 `.item()`，把數值抽出來變成普通的 Python float，讓計算圖可以被釋放。

第三，**batch size 太大**。這個最直觀，就是直接調小。但如果你需要維持大的有效 batch size——比如訓練穩定性的考量——可以用梯度累積。概念是：把四個小 batch 各自做 forward 跟 backward，但只在第四個 batch 結束後才更新參數。效果等同於跑一個四倍大的 batch，記憶體用量卻是小 batch 的規模。

第四，**沒有開混合精度訓練**。FP32 每個數值佔四個 bytes，FP16 只佔兩個。開混合精度之後，大多數運算自動降到 FP16，記憶體用量直接減半，速度通常還更快。PyTorch 內建的 `autocast` 搭配 `GradScaler` 就能做到，幾乎是零成本的優化，沒理由不開。

第五，如果你在跑 Transformer，序列很長，**梯度檢查點**是最後一張王牌。Transformer 的記憶體消耗跟序列長度的平方成正比，序列一長，中間的激活值就爆炸性增長。梯度檢查點的策略是：不存這些中間值，backward 的時候重新算一次。記憶體從線性降到平方根等級，代價是訓練時間大約增加三成。

還有一個現象值得特別提：你看到的 OOM 訊息有時候會說「剩餘空間夠，但分配失敗」，這不是矛盾，這是記憶體碎片化——總量夠，但沒有夠大的連續塊能分配出去。長時間訓練後特別常見，這種情況 `empty_cache()` 更是完全沒用。

診斷的時候可以印出三個數字：目前實際佔用了多少、PyTorch 從 CUDA 預留了多少、以及這次訓練的峰值是多少。這三個數字對比起來，通常能很快告訴你問題出在哪一層。

好，收尾。三個核心要點帶走：

**第一，`empty_cache()` 不是解法，是安慰劑。** 真正的問題要從根本找。

**第二，推論路徑加 `no_grad()`、迴圈裡的 loss 加 `.item()`**，這兩個修改幾乎沒有成本，卻能解決大多數日常 OOM。

**第三，混合精度是最划算的優化**，沒有理由不開；Transformer 長序列的話，梯度檢查點是用時間換空間的有效手段。

CUDA OOM 看起來很嚇人，但大多數情況下，原因很具體，解法也很具體。
