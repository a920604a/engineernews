8 億用戶，單一主庫，沒有分片。這是 OpenAI 在 2026 年初公開的 ChatGPT 資料庫架構，也是讓很多工程師看完之後重新思考自己預設假設的一篇文章。

OpenAI 用的是 PostgreSQL，跑在 Azure 上，搭配將近 50 個讀取副本。讀取副本這個東西本身不稀奇，但 50 個這個數字，加上他們處理連線、複製壓力的方式，值得好好拆開來看。

先說最大的設計決策：為什麼不分片？分片是把資料切割到多個節點的做法，通常被當作超大規模系統的標配。OpenAI 的理由很直接——ChatGPT 的工作負載是讀多寫少。用戶大部分時間是在讀取對話歷史和介面設定，寫入相對集中在幾個特定路徑。這種情況下，讀取副本就能有效分散壓力，不需要動到分片。而且分片的工程代價極高：要改幾百個應用端點，處理跨節點的交易一致性，整個遷移可能要花掉好幾個月甚至幾年。他們選擇把這個決定推遲到真正必要的時候。

接下來是連線問題。PostgreSQL 每個連線對應一個 process，建立連線本身就有約 50 毫秒的開銷。對一個每秒要處理數百萬查詢的系統，這個開銷累積起來是真實的瓶頸。OpenAI 的解法是在每個讀取副本前面放一個 PgBouncer，用 transaction pooling 模式——每次查詢或交易完成後，底層連線立刻回到池子裡，不等 client 斷開。這樣少量的底層連線就能服務大量的並發請求。結果是連線建立時間從 50 毫秒壓到 5 毫秒。每個副本有一個獨立的 Kubernetes deployment 跑 PgBouncer，讓這層的擴展也相對乾淨。

然後是複製壓力。50 個副本代表主庫要維持 50 條 WAL 串流連線，這對主庫的網路和 CPU 是不小的負擔。OpenAI 跟 Azure PostgreSQL 團隊合作測試串聯複製：主庫只連到幾個中間副本，中間副本再往下游轉發。這樣副本數量擴展到 100 個以上，主庫感受到的壓力不會跟著線性成長。

寫入瓶頸的處理方式不是靠副本，而是遷移。把高寫入量的子系統——用量統計、日誌、session 狀態這類東西——移到更適合高寫入的分散式系統，讓 PostgreSQL 專注處理需要強一致性的核心業務資料。背景的批次更新也會設速率限制，避免突發大量寫入衝擊主庫。

這篇文章最有意思的地方，不是技術細節本身，而是決策邏輯。OpenAI 沒有選 NewSQL、沒有換 NoSQL、沒有做分片，因為那些方案的工程成本遠超過它們能解決的問題。他們選的每一個工具——PgBouncer、讀取副本、串聯複製——都是針對已知瓶頸的最小必要解法。

三個帶走的核心觀念：第一，先搞清楚你的工作負載是讀多還是寫多，這決定了你的擴展策略；第二，連線池這種基礎設施優化，效果往往比換架構更快更穩；第三，把工程成本極高的決策推遲到真正撐不住的時候，不是拖延，是務實。PostgreSQL 換掉是最後一個選項，不是第一個。
