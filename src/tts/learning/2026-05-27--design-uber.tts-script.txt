「請你設計 Uber。」

這句話在系統設計面試裡出現的頻率非常高，但每次聽到，都有人腦袋當場空白。原因很簡單——它太大了，大到不知道從哪裡切入。

所以今天我們來拆解這道題，重點不是背答案，而是建立一套思維流程。

---

**第一步，縮小範圍。**

Uber 是個完整的產品生態——乘客 app、司機 app、支付、地圖、評分⋯⋯你如果試圖一次設計所有東西，你什麼都設計不好。

面試一開始，你要做的第一件事就是主動定義邊界。這次只聚焦在「乘客叫車到司機接單」這個核心流程。支付、評分、歷史紀錄先放一邊；地圖服務假設用 Google Maps，不自己設計。

這個動作看起來簡單，但面試官其實在觀察你——有沒有能力自己定義問題，還是只會等人告訴你要做什麼。

---

**第二步，識別核心難點。**

Uber 的本質是一個位置匹配問題：乘客在哪、司機在哪、怎麼把最合適的司機派過去。

這裡有三個值得深挖的子問題。

第一，即時位置更新。司機每隔幾秒就在動，系統要持續接收大量位置資料，這是一個極度 write-heavy 的場景。

第二，附近司機查詢。乘客叫車的瞬間，系統要快速找出附近幾公里內所有空閒司機。這種地理空間查詢，用傳統 SQL 做範圍篩選效能非常差，通常需要專門的地理空間索引。

第三，配對邏輯。找到附近司機之後，派誰？最近的？評分最高的？等待時間最短的？這個決策會影響整體架構設計。

---

**第三步，資料結構與 API 設計。**

我們需要兩張核心資料表。一張記司機的即時位置和狀態——是空閒、忙碌還是離線。另一張記乘客的叫車請求——從哪裡上車、目前配對狀態、最後配到哪位司機。

API 層面，三個核心端點：乘客發起叫車、司機高頻更新位置、以及乘客查詢配對結果——可以用輪詢，或者 WebSocket 推送。

---

**第四步，擴展性取捨，這裡最有意思。**

先算一個數字：假設有一百萬名活躍司機，每四秒更新一次位置，換算下來每秒大約二十五萬次寫入。這個量級直接打進 PostgreSQL 是扛不住的。

業界常見的解法是先寫進 Redis——記憶體操作，延遲極低——再非同步寫到持久化儲存。Redis 本身也支援地理空間查詢，可以直接找出以某個座標為圓心、半徑幾公里內的所有司機，效能遠勝關聯式資料庫的範圍查詢。

另外，位置更新、配對、行程狀態這三個服務應該獨立部署。任何一個流量高峰，不應該拖垮其他服務。

---

整理一下今天的三個核心要點。

第一，面試一開始就主動縮範圍，這不是偷懶，是展示你能定義問題的能力。

第二，系統設計的核心是識別難點，Uber 的難點是高頻地理空間讀寫，工具選型要跟著問題走，而不是先背一個技術清單。

第三，展示取捨思維比說出「正確答案」更重要——因為系統設計本來就沒有標準答案，只有在當前約束下合理的答案。
