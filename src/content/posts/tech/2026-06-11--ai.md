大多數人使用 AI 的方式是：打開 ChatGPT 或 Claude，貼上一個問題，看看回答。這是「在用 AI」。

「善用 AI」不是這樣的。善用 AI 的人在做的事情，更接近「和一個知識淵博但需要明確指引的同事合作」——你要負責提供 context，你要負責驗證輸出，你要知道什麼任務適合交給它、什麼不適合。

以下是讓 AI 真正有用的五個具體做法。

## TL;DR

1. **Context 是關鍵**：模糊的輸入得到模糊的輸出，多給背景讓回答品質翻倍
2. **多輪對話優於單輪**：把複雜任務拆成步驟，邊走邊修正，而不是一次給一個超長 prompt
3. **知道 AI 什麼時候會說錯**：factual recall 類問題最危險，reasoning 類問題相對可靠
4. **接進工作流程**：AI 對話框只是冰山一角，真正的效益在 pipeline 裡
5. **用 AI 做的事要可驗證**：AI 最適合協助你做你有能力驗證輸出的任務

## 1. Context 的品質決定回答品質

AI 模型基本上是個「下一個 token 預測機器」，它只能根據你給的東西生成回應。你給的 context 越精確，它生成的輸出越對你有用。

**壞的 prompt：**
```
幫我寫一個登入功能
```

**好的 prompt：**
```
我在用 Next.js 14 + Supabase，需要一個 email/password 登入功能。
已有 supabase 的 client 設定在 lib/supabase.ts。
需要：登入表單 component、server action 處理登入邏輯、錯誤訊息顯示。
不需要：OAuth、email 驗證流程（已另外處理）。
```

第二個 prompt 給了技術棧、現有程式碼結構、需求範圍、排除項。Claude 或 GPT 生成的程式碼會直接插得進你的 codebase，而不是一個「generic Next.js login」的模板。

實用技巧：在 prompt 的開頭放一段「角色設定」：
```
你是一個熟悉 Rust 的後端工程師，正在 review 以下程式碼，
重點關注 ownership 問題和不必要的 clone。
```

## 2. 多輪對話優於一次搞定

很多人把 AI 當成「一次輸出一個答案」的工具。但對複雜任務，多輪對話的效果遠好於試圖用一個超長 prompt 一次搞定。

**原因：** AI 在一次生成大量輸出時容易失焦。多輪的好處是每一步都可以糾正，方向不對提早修正，不需要從頭來。

**實際操作：**
- 第一輪：確認理解（「先告訴我你打算怎麼做，不用寫程式碼」）
- 第二輪：讓它執行一個具體步驟
- 第三輪：review、指出問題、讓它修
- 重複

這個流程在寫複雜功能、分析設計、撰寫長文時特別有用。把 AI 當成一個需要 pair programming 的工程師，而不是一個 code generator。

---

## 3. 知道 AI 什麼時候會說錯

這是「善用」和「誤用」之間最大的差距。AI 在以下情況最容易給出看起來合理但實際錯誤的回答：

**高風險：**
- **Factual recall**：「某個 library 的版本是多少」、「某個 API 的確切參數」——AI 的訓練資料有截止日期，而且會自信地說出過期的資訊
- **數字計算**：看起來 AI 在算數，但實際上它在預測「這個問題的答案通常長這樣」，不是真正在算
- **最新資訊**：任何 AI 的 knowledge cutoff 之後發生的事

**相對可靠：**
- **推理和分析**：「解釋這段程式碼在做什麼」、「比較兩種架構的取捨」
- **生成任務**：「幫我把這段程式碼重構成更清楚的版本」
- **已知框架內的問題**：「Next.js 的 server action 怎麼寫」（但要確認版本）

**原則：** 任何 AI 說出的具體事實（URL、版本號、函式名稱、benchmark 數字），都要去一手來源確認。

## 4. 把 AI 接進工作流程，不是只用 chat 介面

最大的效益不在聊天框，在 pipeline。

**工程師的典型整合：**

**程式碼 review 自動化：**
```bash
# git commit 前自動請 AI review
git diff --staged | claude "Review this diff: focus on security issues and obvious bugs"
```

**文件生成：**
```bash
# 從程式碼自動生成 API 文件
cat src/api/routes.ts | llm "Generate OpenAPI 3.0 documentation for these routes"
```

**測試生成：**
在 cursor/claude-code 裡，標記一個函式要求「幫我寫這個函式的 unit tests，包含 edge cases」，人工 review 後加進 test suite。

**Claude Code / Cursor / Copilot 的取捨：**

| 工具 | 最適合 | 弱點 |
|------|-------|------|
| Claude Code | 複雜多步驟任務、理解大型 codebase | 每次要給很多 context |
| Cursor | 快速 autocomplete、小修改 | 複雜任務容易跑偏 |
| GitHub Copilot | inline suggestion、IDE 整合 | 不適合需要思考的大型重構 |

## 5. 只讓 AI 做你有能力驗證的事

這是最重要也最容易被忽略的原則。

**反模式：** 讓 AI 寫一個你完全看不懂的模組，然後直接 merge。

問題不是 AI 寫的程式碼一定差——有時候品質很好。問題是**你沒有能力判斷它是否正確**，這讓錯誤進 production 的機率大幅提高。

**善用的版本：**
- AI 協助你寫的程式碼，你能閱讀並理解每一行
- AI 幫你分析，最後的判斷是你的
- AI 生成的文字，你有能力確認事實的部分

AI 最適合「讓有能力的人做得更快」，而不是「讓沒有能力的人繞過能力要求」。

## 跟「只是在用 AI」的差別

| 行為 | 在用 AI | 善用 AI |
|------|---------|---------|
| Prompt 品質 | 一兩句話 | 包含 context、限制、期待格式 |
| 驗證習慣 | 輸出直接用 | 對事實類內容確認來源 |
| 整合深度 | 只用聊天介面 | 接進 git、IDE、CI pipeline |
| 任務範圍 | 什麼都交給 AI | 選擇自己能驗證的任務 |
| 多輪對話 | 一次搞定 | 分步驟、邊走邊修正 |

## 小結

「善用 AI」不是學更多 prompt trick，而是改變你和 AI 協作的心態：你是主導者，AI 是執行者，但它的輸出需要你驗證。

Context 品質決定輸出品質，多輪對話比一次完美 prompt 更實用，而把 AI 接進工作流程的效益遠大於只用聊天框。

最後一點：AI 讓有能力的人更強，這個趨勢不會反轉。現在是練習「如何和 AI 協作」的最好時機，而不是「等 AI 更強再說」的時候。
